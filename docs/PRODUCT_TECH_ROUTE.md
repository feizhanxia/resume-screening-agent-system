# 产品需求与最终技术路线

## 1. 需求整理

### 用户目标

招聘人员安装一个桌面软件后，无需配置 Python、数据库、OCR 或本地服务器，即可：

1. 选择简历根目录；其下每个一级子目录代表一名候选人，内部可递归包含 PDF/DOCX 简历和其他补充材料。
2. 选择结果输出目录。
3. 粘贴岗位 JD 和补充筛选要求。
4. 查看并调整系统自动拆解的硬性条件、评分项和加分项。
5. 批量并行提取和分析全部简历。
6. 在图形表格中排序、筛选、查看证据和标记人工意见。
7. 导出完整 Excel。
8. 按当前筛选结果，把对应候选人的原始材料复制到新目录。
9. 目录新增简历或 JD 变化后增量处理，不重复做无关工作。

### 非功能要求

- 面向 500 个候选人目录，默认八路分析。
- 不漏文件；异常文件也必须出现在清单和进度中。
- 支持任务暂停、取消、崩溃恢复。
- 原始简历默认不移动、不删除、不改写。
- 本地保存数据库、缓存和结果；只有必要的脱敏文本发送给模型 API。
- 安装后直接运行，不要求命令行操作。
- Windows 和 macOS 分别提供安装包。

## 2. 产品形态

这是一个“场景固定、条件动态”的工作流 Agent，而不是通用 Agent 开发平台。

固定的是流程：

```text
选择目录
  → 识别候选人子目录
  → 递归扫描档案包
  → 提取全部 PDF/DOCX
  → 编译 JD 条件
  → 并行分析
  → 覆盖核查
  → 结果筛选
  → Excel 导出
  → 材料整理
```

动态的是 JD、筛选条件、权重、外部事实和最终筛选组合。产品不需要 Agent 市场、自由工具调用、向量数据库、Redis、Celery、浏览器前端或微服务。

## 3. 最终技术选型

| 层 | 选择 | 原因 |
|---|---|---|
| 语言 | Python 3.12 | 文档解析、LLM、Excel 和桌面生态完整 |
| GUI | PySide6-Essentials + Qt Widgets | 原生跨平台，不带 Chromium，不需要本地服务 |
| 工作流 | 自研有限状态机 + asyncio | 场景固定，代码量小，可暂停和恢复 |
| 本地数据库 | SQLite WAL | 单机 500 份足够，无需安装数据库 |
| PDF | pypdfium2 | 文本提取与页面渲染，许可适合打包分发 |
| DOCX | python-docx + XML 顺序遍历 | 覆盖段落和表格，依赖较轻 |
| OCR | Tesseract 优先 + RapidOCR/ONNX 离线兜底 | 按需触发，目标机器无需安装 OCR |
| 模型接口 | OpenAI SDK → DeepSeek V4 | 接口简单，支持 JSON Output |
| 结构校验 | pydantic | 防止无效模型输出污染数据库 |
| Excel | openpyxl | 适合模板、公式和人工列保护 |
| 密钥 | keyring | 保存到 macOS Keychain/Windows 凭据库 |
| 打包 | PyInstaller onedir | 首版构建快、调试直接，按平台冻结 Python 与 Qt |
| 安装器 | macOS DMG；Windows 安装程序 | 符合普通用户使用习惯 |

不采用 Electron/Tauri：Electron 体积大；Tauri 本身轻，但还要处理 Rust 与 Python 文档引擎的双运行时，首版复杂度明显增加。也不采用 FastAPI + 浏览器界面，因为单机场景没有必要运行 HTTP 服务。

## 4. GUI 信息架构

### 页面一：新建任务

- 简历根目录选择器，显示候选人子目录数、PDF/DOCX 数和未归属文件数。
- 输出目录选择器。
- JD 大文本框和补充要求文本框。
- “解析筛选条件”按钮。

### 页面二：确认条件

- 条件表：名称、定义、硬性/评分/加分、权重、是否启用。
- 用户可新增、删除、改写或调整权重。
- 对“前20、985、双一流”等条件提示选择口径或事实来源。
- 用户确认后才开始批量分析，避免错误条件导致 500 份全部重算。

### 页面三：处理进度

- 总文件数、已扫描、已提取、已分析、待复核、失败。
- 八个 Worker 当前任务和总体进度条。
- 单文件状态、重试次数和错误摘要。
- 暂停、继续、取消；关闭应用后允许下次恢复。

### 页面四：候选人结果

- 表格显示姓名、教育、公司、年限、硬性条件、总分、综合状态。
- 可按任意条件筛选和排序。
- 右侧证据面板显示每个结论、页码、原文摘要和不确定项。
- 支持 HR 备注、面试状态、联系状态和负责人。

### 页面五：导出与整理

- 导出完整 Excel、当前筛选结果或待复核清单。
- “整理当前候选人材料”按钮。
- 目标目录预览、预计文件数和重名处理策略。
- 完成后显示复制成功、失败和 manifest 路径。

### 设置页

- DeepSeek API Key，仅写系统凭据库。
- 分析模型、并行度和超时。
- 是否发送姓名、是否自动脱敏联系方式。
- OCR 语言和缓存保留策略。

## 5. 进程与并发模型

```text
GUI 主线程
  │ Qt signal/event
  ▼
后台 Engine 线程：asyncio event loop
  ├─ 候选人任务池（8 个 Worker）
  ├─ 文件提取线程池（全局上限 8）
  ├─ 分析协程池（Semaphore 8）
  ├─ 单数据库写入队列
  └─ 单 Excel/材料写入器
```

GUI 线程只渲染界面，不能执行 PDF、OCR 或 API 请求。Worker 不直接更新 UI、Excel 或共享 JSON；它们返回标准结果事件，由协调器落库并通过 Qt signal 更新界面。

提取与分析形成有界流水线：前面的候选人分析时，后面的候选人可以继续提取；队列设最大长度，避免一次把 500 个档案包全文放进内存。同一候选人的所有文件始终由一个 Worker 负责聚合，避免不同文件被误判为不同候选人。

## 6. Agent 的两个语义环节

### 条件编译 Agent

输入 JD 和用户补充要求，输出结构化条件草案。它不立即处理简历，必须经过用户确认。

### 简历分析 Agent

输入一个候选人档案包内全部已提取文件、稳定事实缓存和本次全部条件，一次返回：

- 通用候选人事实。
- 每个条件的符合/不符合/不确定。
- 分数和置信度。
- 页码与证据摘要。
- 需要外部核验的实体和问题。

当前版本使用用户在设置页选择的单一分析模型，默认是 `deepseek-v4-flash`。一次请求同时判断全部启用条件；超长材料完整分块后合并，模型输出必须通过 pydantic schema 和本地证据校验。材料不足、结论冲突或证据无法对应原文时降级为“不确定”，不再额外调用固定的复核模型。

## 7. 缓存与增量原则

使用三层指纹：

```text
file_hash：单个材料文件是否变化
package_hash：候选人档案包文件集合是否变化
extractor_version：提取逻辑是否变化
criteria_hash + prompt_version + model：判断是否可以复用
```

- 单个文件不变且提取器不变：复用该文件文本。
- 候选人目录新增或删除材料：只提取变化文件，然后重建候选人档案视图并重新判断受影响条件。
- JD 变化：不重新提取文档，只重算变化条件。
- 只改排序或筛选组合：直接查询数据库，不调用模型。
- 新增简历：只加入新文件任务。
- 文件被删除：标记不再当前，不删除历史结果。
- 暂不支持解析的材料仍进入文件清单、包哈希和最终复制清单，并在界面显示“仅归档未解析”，不能静默忽略。

## 8. 材料整理方案

材料整理必须与筛选分离。用户在结果表中应用筛选后，系统取得当前候选人的 `candidate_id` 集合，把候选人的整个原始子目录作为一个整体复制：

```text
<输出目录>/候选人材料/<运行名称>/
├── 入选/
│   ├── 001_张三_<candidate_id短码>/
│   │   ├── 原始简历.pdf
│   │   └── 项目补充材料.docx
│   └── 002_李四_<candidate_id短码>/...
├── 待复核/
└── manifest.xlsx
```

规则：

- 默认 `copy2`，保留原文件时间；绝不默认移动。
- 保留候选人子目录内的相对层级；输出目录名清理非法字符，并使用排名和 `candidate_id` 短码解决重名。
- 复制前显示预览，复制后校验目标文件大小和哈希。
- manifest 记录来源路径、目标路径、筛选条件、复制时间和哈希。
- 再次执行同一任务时跳过哈希相同文件，避免重复副本。

## 9. OCR 与轻量性的取舍

为了“不漏”，最终安装包应包含 OCR，但只对检测为图片型的页面调用。OCR 比文本层提取慢得多，因此结果必须按页缓存。

建议发布一个完整安装包，而不是要求用户自己安装 Tesseract。代价是安装包增加几十 MB；这是完整性所必需的成本。不要引入 PaddlePaddle、浏览器内核或 GPU 运行时，它们会显著放大安装包。

## 10. 许可策略

项目原创代码以 MIT License 公开。PDF 引擎使用 pypdfium2；安装包保留 PDFium 及依赖许可文件。PyMuPDF/MuPDF 是 AGPL 或商业双许可，因此当前版本不引入它。

PySide6 按 LGPLv3 使用，采用可替换的动态库方式打包，并随安装包保留 LGPL 文本和第三方声明。完整清单见仓库根目录 `THIRD_PARTY_NOTICES.md`；这些说明不替代针对具体分发方式的专业法律意见。

## 11. 打包分发路线

1. 开发期始终从源码运行并维护锁定依赖。
2. 首先用 PyInstaller `onedir` 模式在当前平台生成独立应用目录。
3. 在干净虚拟机验证 PDF、DOCX、OCR、Keychain 和 Excel。
4. macOS 构建 `.app`，代码签名、公证后生成 `.dmg`。
5. Windows 在 Windows runner 构建，生成安装程序并签名。
6. 两个平台分别构建；Python 打包工具不能跨平台生成另一系统程序。

不建议一开始追求单文件可执行程序。standalone 目录更容易定位缺失资源、启动更快，也适合携带 OCR 数据；安装器仍会给用户一个普通安装体验。

## 12. MVP 范围

首个可分发版本必须包含：

- PDF、DOCX、图片型 PDF OCR。
- 目录扫描、增量缓存、八路并行和中断恢复。
- JD 条件编译并允许人工确认。
- 结果表、证据、Excel 和材料复制。
- API Key 系统安全存储。
- Windows/macOS 安装包。

暂不包含：邮件和 ATS 集成、多人协作、外部数据库、自动网页搜索、通用插件平台、向量数据库、移动端和自动更新。

## 13. 单人开发周期建议

| 迭代 | 内容 | 预计时间 |
|---|---|---:|
| 1 | GUI 外壳、扫描、SQLite、状态机 | 1 周 |
| 2 | PDF/DOCX/OCR 与完整性审计 | 1–1.5 周 |
| 3 | 条件编译、DeepSeek、八路并行 | 1–1.5 周 |
| 4 | 结果表、Excel、材料整理 | 1 周 |
| 5 | 500 份测试、打包、签名与安装验收 | 1–2 周 |

一个熟悉 Python 的开发者做出首个可安装版本，合理目标是 5–7 周。先在一个操作系统完成闭环，再移植第二个平台，风险最低。

## 14. 最重要的验收顺序

1. 文件零遗漏，异常文件可见。
2. 提取页覆盖和 DOCX 内容覆盖可验证。
3. 条件结论有证据，可表达不确定。
4. 中断可恢复，不重复调用 API。
5. Excel 与数据库一致，人工列不丢。
6. 材料复制准确且绝不破坏原目录。
7. 最后再优化模型评分、界面美观和速度。
