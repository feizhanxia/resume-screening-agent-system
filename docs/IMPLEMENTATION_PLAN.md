# 分阶段开发计划

## 阶段 0：工程、GUI 外壳和安全基线（2–3 天）

交付：

- 初始化 Python 3.12、`pyproject.toml`、PySide6 主窗口、内部 CLI、配置加载和日志脱敏。
- 开发环境变量或系统凭据库密钥加载，启动时检查密钥但不打印。
- SQLite 迁移框架、基本状态枚举和测试流水线。

验收：测试和 lint 可运行；日志、异常和配置输出中搜索不到 API Key。

## 阶段 1：本地扫描与完整提取（5–7 天）

交付：

- 识别一级候选人子目录，递归扫描包内 PDF/DOCX，计算文件哈希与候选人 `package_hash`，完成重复检测和增量变更识别。
- pypdfium2 逐页提取/渲染、python-docx 顺序提取、页面缓存和文档终态。
- 本地 Tesseract 中英文 OCR 及按需触发规则。
- `files`、`pages`、`tasks` 表和基础审计命令。

测试集至少包括：一人多文件、嵌套补充材料、根目录未归属文件、同名候选人目录、目录改名、目录内新增/删除材料、正常文本 PDF、常规/表格型 DOCX、重复、加密、空白、图片型和损坏文档。

验收：目录集合与数据库当前集合完全一致；每个 PDF/DOCX 有状态；中断重启不重复已完成提取。

## 阶段 2：动态条件和 DeepSeek 分析（5–7 天）

交付：

- JD 条件编译器和条件版本。
- DeepSeek V4 客户端、JSON Output、schema 校验和重试。
- 一份简历一次判断全部启用条件。
- 八路异步 Worker、租约和断点恢复。

先用 20 份人工标注简历开发，不追求复杂评分。逐项比较：事实是否正确、证据页码是否正确、缺失信息是否写成不确定。

验收：所有当前文件 × 启用条件均有终态；故意杀掉进程后可以继续；重复运行不重复计费已完成任务。

## 阶段 3：结果界面、Excel 与材料整理（5–7 天）

交付：

- 六表 Excel 输出和人工列保护。
- 可排序、筛选和查看证据的候选人结果表。
- Fact Resolver、本地可信名单导入和事实版本。
- 硬性项、评分项和加分项分层排序。
- 没有完全符合者时输出最接近候选人及差距。
- 按当前筛选结果安全复制候选人材料，生成可追溯 manifest；默认绝不移动或删除原文件。

验收：新增条件只重算受影响判断；修改 JD 不重新读取原始文档；Excel 与数据库 `file_id` 集合一致。

## 阶段 4：500 份稳定性与性能（3–5 天）

测试场景：

1. 40 个候选人目录验证八路同时工作、任务领取和中断恢复。
2. 同一批 50 个候选人目录做串行与八路对照，记录墙钟时间和 API 用量。
3. 500 个候选人目录完整运行，注入 429、网络断开、无效 JSON 和 Excel 占用。
4. 运行中新增、修改、删除和重命名 PDF/DOCX。
5. 只修改一个条件，验证定向重算。

性能目标：八路相对串行至少 4 倍；低于 3 倍时分别测量文档提取/OCR、API 等待、JSON 重试和 Excel 刷新占比。

完成标准：

- 当前 PDF/DOCX 集合、数据库文件集合、结果集合完全一致。
- 任务数等于成功、失败和待复核之和。
- 所有当前文档有提取终态，所有启用条件有判断终态。
- 人工维护字段未被覆盖。
- 任意中断点都能恢复，不重复处理有效终态。

## 阶段 5：安装包与跨平台验收（5–7 天）

- 使用 PyInstaller 的 onedir 模式生成 Windows、macOS 各自构建产物。
- Windows 包装为安装程序；macOS 包装为 `.app` 和 `.dmg`。
- 打包 Python、Qt、PDF/DOCX 解析库、OCR 二进制和中英文语言数据，用户无需另装运行环境。
- 在干净系统测试安装、首次启动、Key 保存、500 份恢复和卸载。
- 后续如需 WorkBuddy，只增加一个启动或导入结果的适配器，不让 WorkBuddy 承担核心任务状态。

## 首轮人工金标

先选 20 份简历和 8–12 个条件，人工建立金标：

- 每个事实的正确值和证据页码。
- 每个条件的符合、不符合或不确定。
- 学校、论文等外部事实的来源。
- 期望的排序区间而不是唯一名次。

评价指标优先级：漏文件率 0；页覆盖率 100%；证据正确率；硬性条件召回率；不确定识别率；最后才是综合排序相关性。
